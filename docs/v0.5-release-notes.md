# Moryn v0.5.0 Release Notes

Moryn v0.5.0 is a context-boundary release. v0.4 established bounded memory,
append-only compaction, and Portable Soul. v0.5 addresses the next practical
failure mode: context can be correct as text and still be unsafe when it crosses
a publication boundary, agent host, repository revision, or machine.

The release adds four related controls:

```text
                 Moryn v0.5 context boundaries

 write ---------- Sync Gate ----------> Git publication
   |               local_only stays local
   |
 host -------- Agent Continuity ------> lifecycle route
   |               capability is negotiated
   |
 repo ---------- Repo Atlas ----------> evidence-bound claim
   |               observations are rebuildable
   |
 read ------ Execution Origin --------> local path access
                   explicit mapping required
```

None of these controls requires a hosted memory service or ownership of the
agent runtime. They extend the existing local store, CLI, MCP server, package
API, and private Git synchronization model.

## 1. Sync Gate and physical local-only routing

Before v0.5, distribution metadata could describe intent, but the ordinary
event tree remained the publication unit. v0.5 separates the bytes physically:

```text
write event
   |
   +-- local_only ------> state/local-events/ ------> local read model
   |                       ignored by Git
   |
   +-- publishable -----> events/ -----------------> sync preflight
                                                    | allow
                                                    v
                                               private Git remote
```

`moryn sync preflight` evaluates pending synchronized events against
`personal_sync`, `trusted_team`, or `public_export`. `shadow` reports findings;
`enforce` returns the decision used by publication. Normal `moryn sync --push`
enforces the personal-sync boundary before staging or committing.

```bash
moryn sync preflight --destination personal_sync --mode shadow
moryn sync preflight --destination trusted_team --mode enforce
moryn sync preflight --destination public_export --mode enforce
```

Receipts contain policy versions, digests, counts, finding codes, and opaque
record/event IDs. They do not contain record bodies or the secret text that
matched a policy. This boundary is prospective: Moryn does not rewrite Git
history or claim to erase local-only text that an older release already
published.

## 2. Agent Continuity Protocol v1

Agent hosts expose different lifecycle surfaces. v0.5 models that difference
instead of assuming every host has the same hooks. Seven operations are mapped
independently: `enter`, `start`, `checkpoint`, `finish`, `handoff`, `abort`, and
`recover`.

```text
requested operation
        |
        v
host capability declaration
        |
        +-- declared hook -----> native_hook
        +-- MCP available -----> mcp
        +-- CLI available -----> cli
        +-- none --------------> unavailable
```

```bash
moryn continuity negotiate --host codex
moryn continuity negotiate --host opencode --no-native-hooks
moryn continuity transfer \
  --project-id my-project \
  --source-host codex \
  --target-host opencode
```

A transfer plan orders source checkpoint, source handoff, target enter, and
target recovery while preserving one workspace identity. Codex and Claude Code
integrations recover after compaction through `SessionStart(source=compact)`.
Generated integrations do not install a PostCompact handler, and v0.5 no longer
reports one as native. OpenCode uses MCP or CLI unless the operator installs a
separate lifecycle plugin.

Negotiation is not a probe of host configuration files. In the absence of
explicit transport flags, defaults come from the adapter registry; each route
records whether its availability came from that registry or from the caller.
Use `--no-native-hooks`, `--no-mcp`, and `--no-cli`, or their source/target
transfer variants, when the runtime differs from the generated integration.

## 3. Repo Atlas v2

Repo Atlas separates machine observations from human or agent interpretation:

```text
Git-tracked files
      |
      v
file/symbol/dependency observations   local, rebuildable, content-free
      |
      v
authored claims                       append-only, evidence-bound
      |
      v
onboarding / request_path / release_impact lenses
```

The scanner records paths, SHA-256 digests, sizes, line counts, language and
role classifications, and bounded package metadata. For JavaScript and
TypeScript families it also records bounded AST symbols and static dependency
edges. Source text and the repository's absolute path are not persisted in the
snapshot.

```bash
moryn repo-atlas scan --repo .
moryn repo-atlas claim --repo . \
  --project-id my-project \
  --statement "src/server.ts owns the request boundary" \
  --symbol 'src/server.ts#handleRequest' \
  --evidence tests/server.test.ts \
  --agent codex
moryn repo-atlas view --repo . --lens release_impact
moryn repo-atlas reverify --repo . --claim-id <claim_id> --agent codex
```

File evidence becomes stale when the file digest changes. Symbol evidence
becomes stale only when that symbol changes or disappears, reducing invalidation
from unrelated edits in the same file. Reverification appends a revision to the
same claim identity. Reusing that identity with different metadata now fails
instead of silently returning the older claim.

Dependency edges are static observations, not proof that a runtime path runs.
Unsupported languages and parse failures retain file evidence; Moryn does not
invent symbols to fill a gap.

## 4. Execution origin and workspace mapping

Git synchronization copies an event; it does not move the filesystem where the
event occurred. v0.5 derives lineage from immutable `source.device_id` values:

| Lineage | Meaning | Required action |
| --- | --- | --- |
| `current_device_only` | all known mutations came from this device | verify that the path exists |
| `remote_device_only` | all known mutations came from another device | resolve an explicit workspace mapping |
| `multiple_devices` | mutations came from several devices | inspect timeline and map the relevant origin |
| `unknown` | legacy or incomplete provenance | verify origin before access |

The execution-origin index is local and rebuildable. It stores only opaque
device IDs, unknown-source state, creation/latest device IDs, and event counts.
It excludes event bodies and paths. Manifest checks prevent a concurrent write
from publishing a mixed-generation index; an uncertain read fails lineage to
`unknown` rather than guessing.

Workspace mappings translate a source-device root into an existing local
checkout:

```bash
moryn workspace map set \
  --project-id my-project \
  --source-device-id <source_device_id> \
  --source-root /source/work/repo \
  --local-root /local/work/repo

moryn workspace map resolve \
  --project-id my-project \
  --source-device-id <source_device_id> \
  --source-path /source/work/repo/src/server.ts
```

Mappings are device-local configuration under `state/workspace-mappings/`.
They are not events and are not synchronized. Longest-prefix selection and
realpath containment reject missing targets and symlink escapes. Equal-looking
paths on two machines never create an implicit mapping.

## 5. Operational hardening

- Dashboard shared-copy sync is one confirmed action with bounded receipts,
  safe rebase, no force push, and explicit conflict failure.
- Dashboard JSON POST bodies are capped at 1 MiB.
- Project alias repair requires explicit identity evidence.
- Host hook execution has bounded input, deadlines, process cleanup, and local
  pending-follow-up receipts.
- Execution-origin indexes validate internal source/creation/latest device
  consistency before use.
- Production dependency overrides resolve current `fast-uri`, Hono, and
  `ip-address` advisories; MCP SDK 1.30 accepts the Hono 2.x adapter directly.

## 6. Compatibility and upgrade boundary

Moryn v0.5 opens v0.2, v0.3, and v0.4 stores in place. No migration command or
event-history rewrite is required. Derived artifacts can be rebuilt from events;
a Repo Atlas v1 snapshot triggers a complete v2 rescan.

The mixed-version boundary matters for publishing. A v0.4 client can read
ordinary synchronized records but does not know the v0.5 local event journal,
Sync Gate enforcement, execution-origin index, workspace mappings, or Repo Atlas
v2 claims. Devices that push to the same remote should use the same release
line.

Install and verify:

```bash
npm install -g @richardyu114/moryn@0.5.0
moryn --version
moryn health check --project . --host <host>
moryn rebuild
```

See [v0.5 migration](v0.5-migration.md) for the operational checklist and
[Context Infrastructure](context-infrastructure.md) for exact command, MCP, and
safety contracts.

## 7. Release verification

The release gate requires build, typecheck, lint, the full test suite, v0.4
regression acceptance, v0.5 context-boundary acceptance, package-content and
privacy audits, lifecycle/host/sync/upgrade/large-store smokes, a production
dependency audit, and a clean install of the packed artifact with dependencies
resolved from the public npm registry. The Git tag, npm package, and GitHub
Release are created only after the exact release commit passes these checks. A
second clean install from the published `0.5.0` package verifies the registry
artifact after publication.
