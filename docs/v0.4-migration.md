# Moryn v0.4 Migration

Moryn v0.4 opens v0.2 and v0.3 stores in place. It does not rewrite the event
log, require a migration command, or silently compact existing history. This
guide applies to the `0.4.0` release. Install the versioned npm package:

```bash
npm install -g @richardyu114/moryn@0.4.0
moryn --version  # 0.4.0
```

## Upgrade

Upgrade and verify the local integration:

```bash
npm install -g @richardyu114/moryn@0.4.0
moryn health check --project . --host <host>
```

Snapshots and retrieval indexes are derived data. Moryn rebuilds them lazily
when the event manifest or v0.4 working-set selection no longer matches. The
append-only event history remains authoritative.

## What changes on first read

Legacy records receive conservative inferred views for three independent axes:

- abstraction layer: L0 evidence, L1 episodic, L2 semantic/procedural, or L3
  identity;
- trust: raw, candidate, canonical, quarantined, or legacy unknown;
- retention: hot, warm, cold, or purged, with independent pinned and
  `never_forget` safeguards.

These views do not mutate the source record. Existing `archived` records map to
the cold tier and stay outside normal boot/recall. Purged records are also
excluded by default. A targeted timeline or source-expansion request can still
inspect retained evidence.

Normal project retrieval is now selected through deterministic record and
token budgets. L3, pinned, and `never_forget` records are mandatory and may
produce an explicit overflow report. Moryn does not silently truncate them to
make a budget appear satisfied.

## Manual unified compaction is confirmation-gated and reversible

The manual unified workflow exposes preview and plan phases before apply through
`moryn memory compact preview|plan|apply|restore` and the matching
`memory_compaction_preview|plan|apply|restore` MCP tools. Preview and plan are
non-mutating. Unified apply and restore require explicit `--confirm` or
`confirm: true`. Apply writes an auditable rollup, verifies that it can be read
back, and only then appends source archive/cold events. A stale or partially
applied plan is resumed or rejected deterministically.

Compaction preview now defaults to `include_private: false`. Private-classified
sources in the selected scope become a count-only omission blocker. This covers
private/secret/sensitive tags and legacy Episode content marked
`privacy: "private"` or `distribution: "local_only"`: no private ids, claims,
handoff content, or record text are returned, and the artifact is not
apply-ready. Explicit `--include-private`, MCP `include_private: true`, or
Engine `include_private: true` is bound into the preview/plan digest and is
revalidated at apply time. The exported pure planner has the same default; pass
`previewMemoryCompaction(records, { include_private: true })` explicitly when
planning over an authorized private record set.

This manual confirmation gate is separate from finalization: `agent_finish` may
still apply a safe, fully covered Session Fold automatically. It does not bypass
coverage, privacy, digest, conflict, or protected-content checks.

Archive/cold is a reversible logical state. Restore appends new state events; it
does not delete the rollup or edit earlier events. Automatic physical purge is
not part of v0.4. If content was already pushed to a Git remote, changing its
logical retention state does not erase it from Git history.

Before applying a plan, review its:

- source and destination record/token counts;
- coverage attestation and source digests;
- public/private boundary;
- conflicts, quarantine, protected content, and unique evidence blockers;
- sync impact and logical restore scope.

Compressed history remains inspectable without returning cold records to the
normal working set:

```bash
moryn memory expand <record_id> --max-depth 2 --max-records 100
```

## Historical recovery and outcome feedback

Normal recall remains bounded and favors the current logical working set. When
that pass is missing or incomplete, v0.4 may perform one bounded, read-only
historical search over cold, archived, logically hidden, and budget-omitted
records. It does not silently unarchive a source. When the recovered evidence is
verified as useful, Moryn writes a compact current Learning record linked to the
historical source, so future recall does not need to replay scattered history.

Recall itself is still read-only. A host may submit one explicit final outcome
with `moryn memory feedback <record_id> --outcome
recalled|used|verified|rejected --idempotency-key <interaction_id>`. Moryn stores
record-level outcome metadata, not the original query or generated answer.
`used` and `verified` improve later ranking, `rejected` lowers it, and `recalled`
is neutral. Reusing an idempotency key with different content is rejected.

## Automatic maintenance and remembered aliases

A newly committed checkpoint and `agent_finish` may each apply at most one
proof-gated public project semantic merge. Sources must pass topic, conflict,
privacy, digest, coverage, protected-content, real-token, and strict count
reduction checks. Source events remain append-only and inspectable. An
idempotent checkpoint replay does not run maintenance twice. v0.4 intentionally
does not add a periodic background scheduler.

After the user approves an exact Dashboard project repair, Moryn records a
directional portable alias attestation. Later eligible public records under that
same alias can migrate automatically by exact record-id revision. Private, Soul,
conflicted, protected-state, unknown, and reverse mappings still require manual
review.

## Dashboard deployment

Dashboard GET requests are read-only. Explicit POST actions are auditable store
mutations and work both when connected directly and through a reverse proxy.
The Dashboard server does not provide multi-user application authorization;
deployments exposed beyond a trusted single-user boundary must enforce access
control at the network or proxy layer. Loading or refreshing a view does not
approve a migration or compaction plan.

## Portable Soul

v0.4 introduces versioned User Soul and Agent Persona profiles. Existing
unversioned `kind: soul` records remain readable as a compatibility source; no
automatic rewrite or activation occurs.

Soul clauses are distributed independently:

- `personal_sync` clauses are stored as append-only profile projections and may
  travel through the configured private Git store. An approved projection may
  include a metadata-only, integrity-checked approval attestation, never
  `local_only` clause text;
- `local_only` clause payloads remain under the store's ignored `state/`
  directory and are never included in the sync projection.

Drafts do not become effective until explicitly approved. Approval and rollback
create immutable receipts and new revisions. If synchronized devices create
competing active heads, status reports a conflict and Effective Soul can fall
back to the last known good approved revision.

Effective Soul compilation applies subject, project scope, distribution,
precedence, and character/token budgets. Mandatory boundary or identity clauses
that do not fit block hook-context preparation. `host_context_prepared` and
proof scope `hook_output_prepared_not_host_acknowledged_or_obedience` mean only
that compiled text was prepared for supported hook output; they do not prove
stdout transport, Host acknowledgment, or model obedience.

### Security and privacy limitations

A synchronized portable projection exposes
`full_revision_id`, and that revision ID is currently an unsalted content
fingerprint of the full revision, including any `local_only` clause text. The
text itself is not synchronized, but a low-entropy local clause may be tested by
offline guessing against the ID. v0.4 does not claim to prevent this. A future
format should decouple portable identity from private content with a
device-local overlay or randomized local identity.

The metadata-only approval attestation provides a content-integrity chain, not
a device-key signature. A principal with write access to the store can fabricate
an internally consistent revision and attestation chain; ordinary Git access
control remains part of the trust boundary. For a mixed revision received from
another device, Moryn can verify only the portable projection digest, not the
unsynchronized local overlay or its private clause content.

When restoring local-only clauses over a partial remote projection, Moryn uses
the nearest local full revision on that remote revision's parent ancestry. It
does not carry a device-local overlay across an unrelated concurrent branch. If
no local ancestor is available, the derived draft contains only the explicitly
authored and portable parent clauses; review local context before approval.

Moryn does not overwrite `AGENTS.md`, `CLAUDE.md`, or user-owned host settings
to synchronize Soul.

The supported management surface is `moryn soul status`, `moryn soul draft`,
`moryn soul approve <revision_id> --confirm`, and `moryn soul rollback
--profile-id <profile_id> --to-revision <revision_id> --confirm`. Status is
metadata-only; review clause content in the draft response before approving its
revision ID.

## Privacy and backup

The store `.gitignore` excludes `config.json`, `.moryn/`, `snapshots/`,
`indexes/`, and `state/`. v0.4 stores local full Soul projections and local
compaction/approval/compilation/hook-preparation receipt copies under `state/`
with restrictive directory and file modes. The synchronized approval
attestation described above is metadata-only and integrity-checked. Before
pushing an older manually initialized store, confirm its tracked files:

```bash
git -C <store-path> status --short
git -C <store-path> ls-files state .moryn config.json snapshots indexes
git -C <store-path> log --all --oneline -- state .moryn config.json snapshots indexes
```

Do not add these paths to Git. Public package and release checks reject them.
Sync also rejects a local or remote `main` history if any reachable commit ever
touched one of these paths, before checkout, rebase, or push. A later
`git rm --cached` commit cleans only the tip; it does not remove previously
synchronized private blobs. Rewrite the dedicated store repository's history
with an appropriate reviewed backup, or migrate the event-only history into a
new clean private repository, before retrying v0.4 sync.

## Downgrade

The event log remains valid append-only JSON, but v0.3 does not understand v0.4
retention selection, rollup transactions, or versioned Soul management. A v0.3
runtime may treat new records as ordinary compatible records and will not
prepare Effective Soul hook context. Prefer upgrading all active hosts before
creating Soul revisions or applying compaction plans.

If a temporary downgrade is necessary, stop v0.4 maintenance writes first,
retain the complete event log and local `state/` backup, and do not try to
delete v0.4 events. Re-upgrade to v0.4 to inspect receipts or logically restore
archived sources.

## Post-upgrade checklist

1. Run `moryn health check --project . --host <host>`.
2. Open the dashboard and inspect Memory Maintenance before applying any
   compaction plan.
3. Confirm the active working-set size and mandatory overflow are expected.
4. Create Soul profiles as drafts, inspect the metadata-only status, and approve
   only the intended revision.
5. Start a fresh Codex or Claude Code session and verify the compilation and
   hook-preparation receipts report `host_context_prepared` without treating it
   as Host acknowledgment.
6. Push only after `git status` confirms that local `state/` payloads are not
   tracked.
